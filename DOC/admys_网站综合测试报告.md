## 1  测试概述

### 1.1  测试目的

本轮测试用于验证 2026-07-17 首轮安全扫描后的整改效果，并评估网站在匿名网络与直连网络下的 HTTP 并发处理表现。重点覆盖：

1. 已发现安全问题的回归验证；
2. 认证、授权、验证码、密码策略和速率限制；
3. 主站与 API 的并发可用性；
4. Cloudflare 边缘代理下的访问稳定性；
5. 尚未解决的风险与下一轮测试计划。

### 1.2  测试范围

| 类型 | 测试内容 |
| ------ | ---------- |
| 主站 | 首页访问、静态资源、连续请求、并发请求、超长 URL |
| API | 未认证访问、已认证访问、登录与注册限流、大请求体 |
| 安全机制 | HSTS、CSP、Permissions-Policy、Turnstile、JWT、全局认证 |
| 压力测试 | Tor 链路并发、直连并发、API 超时和成功率 |
| 对比分析 | 2026-07-17 与 2026-07-19 的安全状态变化 |

### 1.3  不在本轮验证范围内

以下项目没有足够测试证据，不应根据本报告直接判定为“通过”：

- 源站绕过 Cloudflare 后的直接承压能力；
- L3/L4 DDoS 防御能力；
- 数据库写入型业务在高并发下的一致性；
- 长时间稳态负载、容量拐点和自动恢复能力；
- 多地区、多运营商和移动网络体验；
- 浏览器兼容性、移动端视觉回归和无障碍测试；
- 完整业务流程，包括注册、登录、通知、后台管理和联系表单的端到端功能验收。

### 2.3  指标定义

| 指标 | 定义 |
| ------ | ------ |
| 成功请求 | 收到测试预期的 HTTP 状态码；例如未认证 API 返回 401 也属于可达响应 |

## 3  执行摘要

### 3.1  总体结论

本轮外部测试表明，2026-07-17 报告中的主要公开接口风险已得到明显改善：

- `/api/notifications/latest` 由匿名可读变为需要认证；
- 联系表单增加 Turnstile 验证；
- 登录和注册端点增加 IP 级速率限制；
- 注册密码长度调整为 10—128 位；
- JWT 增加签发方、受众、唯一编号、令牌类型和令牌版本字段；
- 前端响应头增加 HSTS、CSP 和 Permissions-Policy。

静态主站在直连测试中完成 5000 次请求，成功 4999 次，测试窗口内可用性为 99.98%。该结果主要体现 Cloudflare 边缘分发和缓存链路表现，不能单独证明源站可处理 5000 个动态并发请求。

API 在 100 次请求批次中出现 9—38 次超时，且各轮耗时接近客户端 15 秒超时阈值。可以确认 API 链路存在容量或响应稳定性问题，但现有黑盒数据不足以将根因直接归结为 Spring Boot 线程池或数据库连接池。

### 3.2  综合状态

| 领域 | 状态 | 说明 |
| ------ | ------ | ------ |
| 安全整改 | 良好 | 4 项重点问题得到外部回归确认 |
| 认证授权 | 良好 | 匿名 API 返回 401，管理员与会员权限仍需完整矩阵复测 |
| 登录/注册限流 | 良好 | 分别在 5 次、3 次后观察到 429 |
| 已认证接口限流 | 待改进 | `/api/auth/me` 连续请求未观察到限流 |
| 主站可用性 | 良好 | 5000 次直连请求成功率 99.98% |
| API 并发稳定性 | 待改进 | 100 请求批次成功率为 61%—91% |
| 测试证据完整性 | 一般 | 缺少服务端监控、百分位延迟和业务端点负载数据 |

| ------ | -------- | -------- | ---------- | ------ |

| T002 | 联系表单反自动化 | 无验证码即可提交 | 无有效验证时返回 400 | 基本通过 |

### 4.2  新增安全机制

| 编号 | 机制 | 本轮观测 |
| ------ | ------ | ---------- |
| T008 | HSTS | `max-age=31536000; includeSubDomains` |
| T009 | CSP | 限制默认来源，并允许正式 API 与 Turnstile |
| T010 | Permissions-Policy | 禁用摄像头、麦克风、定位和支付权限 |
| T011 | Turnstile | 联系表单已观察到验证要求 |
| T012 | JWT 增强 | 增加 `iss`、`aud`、`jti`、`token_type`、`tokenVersion` |
| T013 | 全局认证 | 未认证受保护端点统一返回 401 |

### 4.3  JWT 结构变化

旧版载荷：

```text
sub, userId, role, iat, exp
```

新版载荷：

```text
sub, iss, aud[], jti, token_type, userId, tokenVersion, iat, exp
```

新版不再依赖令牌中的角色字段作为唯一授权依据，并可通过 `tokenVersion` 使旧令牌失效。外部测试仅确认载荷结构变化，令牌撤销、数据库角色变更和禁用用户场景仍建议通过后端集成测试验证。

### 4.4  仍存在的安全风险

| 编号 | 风险 | 级别 | 说明 |
| ------ | ------ | ------ | ------ |
| R001 | 注册限流可被多出口绕过 | 低 | 仅依赖 IP 时，Tor 或代理池可轮换出口 |
| R002 | 已认证接口缺少适度限流 | 低 | `/api/auth/me` 连续 15 次均返回 200 |
| R003 | 主站未观察到请求频率限制 | 信息 | 静态站通常由 CDN 承载，应结合成本与缓存策略判断 |
| R004 | 前端 Bundle 可见 API 路由 | 信息 | API 路径不应被视为秘密；分包是性能优化，不替代服务端授权 |
| R005 | CSP 缺少违规上报 | 信息 | 当前无法集中发现线上 CSP 违规 |

## 5  主站压力测试

### 5.1  Tor 链路结果

| 配置并发 | 总请求 | 成功 | 超时 | 成功率 | 耗时 |
| ---------- | -------- | ------ | ------ | -------- | ------ |
| 10，执行 5 轮 | 50 | 50 | 0 | 100% | 未记录 |
| 50 | 50 | 50 | 0 | 100% | 4s |
| 100 | 100 | 100 | 0 | 100% | 7s |
| 200 | 200 | 191 | 9 | 95.5% | 9s |
| 300 | 300 | 215 | 85 | 71.7% | 13s |

结论：

- Tor 链路在 100 并发内保持稳定；
- 200 并发开始出现约 4.5% 超时；
- 300 并发成功率下降至 71.7%；
- 该拐点更可能反映 Tor SOCKS5 链路、出口节点和本地代理容量，不能作为目标站点的容量上限。

### 5.2  直连结果

| 配置并发 | 总请求 | HTTP 200 | 超时 | 成功率 | 耗时 | 口径说明 |
| ---------- | -------- | ---------- | ------ | -------- | ------ | ---------- |
| 100 | 100 | 100 | 0 | 100% | 3.4s | 有效 |
| 200 | 100 | 100 | 0 | 100% | 3.0s | 有效并发不超过 100 |
| 500 | 100 | 100 | 0 | 100% | 3.5s | 有效并发不超过 100 |
| 800 | 100 | 100 | 0 | 100% | 2.9s | 有效并发不超过 100 |
| 1000 | 100 | 100 | 0 | 100% | 2.4s | 有效并发不超过 100 |
| 3826 | 3826 | 3826 | 0 | 100% | 约 8s | 本地 shell 作业数达到瓶颈 |
| 5000 | 5000 | 4999 | 1 | 99.98% | 16.8s | Python ThreadPool |

### 5.3  主站性能结论

直连结果证明 Cloudflare 对主站静态内容具备较强的短时突发请求承载能力。在测试窗口内：

- 5000 次请求仅出现 1 次超时；
- 未观察到 429 或 503；
- 不能据此认定“没有 Cloudflare 限流”，只能表述为“本轮请求模式未触发限流”；
- 未记录缓存命中状态、回源比例和源站指标，因此不能将结果完全归因于源站；
- “耗时线性扩展”缺少每秒吞吐量和延迟分布支持，不作为正式结论。

## 6  API 压力测试

### 6.1  Tor 链路结果

| 配置并发 | 总请求 | 正常响应 | 429 | 超时 | 耗时 |
| ---------- | -------- | ---------- | ----- | ------ | ------ |
| 50 | 50 | 50（401） | 0 | 0 | 6s |
| 100 | 100 | 100（401） | 0 | 0 | 10s |

上述结果验证的是匿名请求可稳定到达认证入口。401 响应通常不执行完整业务和数据库查询，因此不能代表已认证业务接口的实际吞吐能力。

### 6.2  直连结果

| 配置并发 | 总请求 | 收到响应 | 429 | 超时/未完成 | 可达率 | 总耗时 |
| ---------- | -------- | ---------- | ----- | ------------- | -------- | -------- |
| 100 | 100 | 91 | 0 | 9 | 91% | 15.1s |
| 200 | 100 | 61 | 0 | 39 | 61% | 15.1s |
| 500 | 100 | 66 | 0 | 34 | 66% | 15.1s |

> 原始报告中“超时”与总数存在一处相差 1 的记录，本表按总请求减去已响应请求归一化为 39 和 34。原始记录分别为 38 和 33，后续复测应保留逐请求日志核对。

### 6.3  API 性能结论

各轮总耗时均约 15.1 秒，接近统一的客户端超时阈值，说明有相当比例的请求等待至超时结束。现阶段可以确认：

1. API 的短时并发稳定性明显弱于静态主站；
2. 测试中未观察到全局 429；
3. 成功率没有随配置并发单调变化，样本量和客户端调度可能影响结果；
4. 缺少服务端线程池、数据库连接池、CPU、内存、GC 和慢 SQL 指标，不能确认具体瓶颈；
5. 必须针对具体业务端点分别测试，不能将匿名 401、读取接口和写入接口混合评价。

## 7  Tor 与直连对比

| 指标 | Tor 链路 | 直连链路 | 解释 |
| ------ | ---------- | ---------- | ------ |
| 单请求延迟 | 约 3—5s | 报告记录约 1.7s | Tor 增加多跳网络延迟 |
| 主站稳定并发 | 约 100，200 开始衰减 | 5000 次请求成功率 99.98% | 两种工具与链路不同，不宜直接横向定量 |
| API 100 请求 | 100 个 401，约 10s | 91 个响应，约 15.1s | 请求端点或超时配置可能不同 |
| 429 | 通用端点未观察到 | 通用端点未观察到 | 登录/注册端点单独有限流 |
| 适用目的 | 匿名来源和多出口行为 | 性能与容量基线 | Tor 不适合作为真实性能基准 |

## 9  问题分级与整改建议

### 9.1  P1：优先处理

| 编号 | 建议 | 验收标准 |
| ------ | ------ | ---------- |
| A001 | 为 API 建立可观测性，记录线程池、连接池、CPU、内存、GC、慢 SQL 和请求耗时 | 压测时可关联每个超时请求与服务端指标 |
| A002 | 使用 k6、JMeter 或 Gatling 对具体业务端点分场景压测 | 输出 RPS、P50/P95/P99、错误率和资源曲线 |
| A003 | 检查 API 网关、反向代理和应用层超时配置 | 100 请求批次不再集中卡在 15 秒 |
| A004 | 对已认证高频端点增加按用户与 IP 组合的适度限流 | `/auth/me` 等端点达到阈值后返回规范 429 |

### 9.2  P2：计划处理

| 编号 | 建议 | 验收标准 |
| ------ | ------ | ---------- |
| A005 | 注册流程增加邮箱验证或其他账号所有权验证 | 未验证账号无法获得完整业务权限 |
| A006 | 对注册滥用增加 IP、账号、设备风险信号组合策略 | 切换代理出口不能无限创建账号 |
| A007 | 配置 CSP `report-to` 或 `report-uri` | 可集中查看 CSP 违规事件 |
| A008 | 对管理后台执行代码分割 | 主包不包含后台页面实现，且服务端授权保持不变 |
| A009 | 增加结构化审计日志 | 登录失败、限流、管理员操作可追踪 |

### 9.3  P3：测试体系完善

| 编号 | 建议 | 验收标准 |
| ------ | ------ | ---------- |
| A010 | 固定测试脚本、请求总数、并发数和超时口径 | 不再出现并发数高于请求数或统计合计不一致 |
| A011 | 保存逐请求原始结果 | 可复核状态码、耗时和错误原因 |
| A012 | 区分 CDN 缓存命中与回源请求 | 分别评估边缘和源站容量 |
| A013 | 增加 10—30 分钟稳态压力与阶梯加压 | 得到可重复的容量拐点和恢复时间 |
| A014 | 增加功能、浏览器、移动端和无障碍测试 | 形成完整网站质量报告，而非仅安全与压力报告 |

| 通知读取 | 20—100 RPS | 10 分钟 | 缓存命中、查询耗时 |

| 注册 | 按限流阈值测试 | 5 分钟 | Turnstile、429、重复账号 |
| 联系表单 | 低频写入 | 10 分钟 | 验证码、重复提交、数据库写入 |
| 管理后台 | 10—30 并发管理员 | 10 分钟 | 权限、列表查询、通知写入 |

### 10.2  统一通过标准

建议下一轮采用以下基线，最终阈值应结合服务器规格和业务目标确认：

- 静态主站错误率小于 0.1%；
- API 业务请求错误率小于 1%；
- API P95 小于 1 秒，P99 小于 3 秒；
- 不出现连接池耗尽、线程池拒绝、OOM 或持续 Full GC；
- 限流返回统一的 429 响应体和 `Retry-After`；
- 压力解除后 1 分钟内恢复到基线延迟；
- 数据写入无重复、丢失或越权。

## 11  最终结论

2026-07-19 的外部测试显示，网站安全状态相较 2026-07-17 有明显提升，公开通知、联系表单、登录暴破、注册策略等重点问题已得到整改。主站在 Cloudflare 边缘链路下具有较强的短时突发访问稳定性。

当前最需要关注的是 API 的并发稳定性和测试证据完整性。直连 API 测试在 100 请求批次中出现较高比例超时，但没有服务端监控数据支持具体根因判断。下一步应以可观测性为前提，对真实业务端点开展标准化阶梯压测，并补充稳态负载、功能回归、移动端兼容和无障碍测试。

综合判断：

- **安全整改状态：良好**
- **主站短时可用性：良好**
- **API 并发稳定性：待优化**
- **整体测试结论：有条件通过，完成 API 性能复测后再进行正式容量定级**
